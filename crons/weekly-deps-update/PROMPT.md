# Weekly dependency update

Run in an isolated checkout with GitHub and package-registry access. Read `AGENTS.md`, fetch `origin/main`, and use the `America/Los_Angeles` date as the run key. The scheduler supplies credentials and keeps the run log; never rely on a maintainer's local `.codex`, `.claude`, or ignored `plan/` state. Find the dedicated GitHub issue titled `[automation] weekly-deps-update ledger` (create it with label `auto-deps` if absent). Before scanning, check its comments for a terminal entry with today's run key; if one exists, report duplicate and stop, even if that run's PR has merged or closed. Check recent `auto-deps` PRs and the existing `[deps] weekly summary` issue too. If an `auto-deps` PR is open, do not start another; inspect or continue its review/CI state within the same limits below. Do not ask the maintainer for ordinary triage decisions.

Install with `pnpm install --frozen-lockfile`; collect `pnpm outdated --recursive --format json` and `pnpm audit --json` (the audit command may exit nonzero when it finds advisories). Classify direct upgrades by actual semver change, including pre-releases and zero-major versions conservatively. A high/critical security advisory takes priority, but its PR is always human-merge-only. Otherwise choose **one** allowlisted patch upgrade, preferring the package least recently upgraded according to Git/PR history. Minor/major updates are issue-only. Do not create work to fill the schedule.

Do not automatically upgrade `react`, `react-dom`, `vite`, `rolldown-vite`, `marked`, `@vitejs/plugin-react`, `astro` or Astro plugins, `drizzle-orm`, `drizzle-kit`, `better-auth`, or `playwright`, even for patches. Treat uncertain packages as excluded; record them for human evaluation. Safe candidates can include types, lint/test tools, and low-risk CLI utilities, but still require actual validation. One package per PR. A security exception may involve a normally excluded package or non-patch update, but clearly label it for human review and **never self-merge**. Do not edit product code to rescue an upgrade.

Update only the necessary dependency declarations and `pnpm-lock.yaml`; avoid unrelated lockfile churn. Try at most three candidates if validation fails. Require `pnpm lint:check` with zero warnings, `pnpm typecheck`, `pnpm test`, `pnpm build`, and the repository's full `pnpm verify` before PR. Run E2E if available and state when it was not. Compare viewer bundle size to the same-environment `origin/main` baseline: an existing oversized bundle is not itself a failure, but this PR must not increase it by more than 1%. If validation fails for non-mechanical reasons, abandon that candidate and record why. Do not change application code, tests, or CI to make a dependency pass.

Create at most one normal patch PR labeled `auto-deps`; document old/new versions, upstream changelog or its absence, the narrow diff, checks, E2E status, and bundle comparison. Security PRs must say `Security fix — human review and merge required`. Request `@codex review` for the current head. An acceptable review is a `chatgpt-codex-connector` formal review on the current SHA or its issue comment containing `Codex Review:` and a matching `Reviewed commit`. Read formal reviews, issue comments, inline comments, all required checks, and merge state. Poll no more often than every 60 seconds and no longer than 15 minutes per head; at most three reviewed heads. If behind, update normally, then repeat CI and review for the new SHA. Only fix dependency declarations, lockfile, or routine-introduced mechanical issues under 30 new diff lines; revalidate and re-review. For breaking changes, behavior risk, non-mechanical red CI, or missing coverage, close or leave blocked with an explanatory issue. Never use `--admin` or push to `main`. Squash-merge a normal patch only when the current head has valid Codex review, **no unresolved actionable Codex finding of any priority (including P2)**, no changes-requested review, and all required checks are success/skipped. Only explicitly non-actionable nits may be left. Always leave security PRs open for a human even if review and CI pass. Do not create another monitor or cron to finish the PR.

For minor/major/excluded candidates, create or update **one** open issue titled `[deps] weekly summary ...` labeled `auto-deps`; avoid duplicate weekly issues. At the end of every run, including a no-candidate skip or blocked PR, append one terminal entry to the dedicated ledger issue with the run key, base SHA, candidate/failed-attempt summary, and PR/issue outcome. If the run fails before reaching a terminal outcome, do not record it as terminal; a retry may resume. Include high/critical advisory evidence, remaining safe patches, failed attempts, and PR/issue links in the scheduler's final run report. No eligible candidate is a valid no-PR result. Never publish or bump this repository's own version.
